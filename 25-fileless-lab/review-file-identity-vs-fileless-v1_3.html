Scope

Strong document. The coverage table in §5.3 and the refusal to overclaim on F-4 and F-8 are what make it credible, and publishing the lab defects in Appendix G is unusual and welcome. The criticism below is almost entirely about the enforcement design rather than the analysis: the prose describes a gate that Appendix C does not implement, and the exemption that containers require looks reachable by an unprivileged attacker.

Blocking for enforcement

Each of these would either break production or leave the gate bypassable if M-03 were switched from detect to enforce as written.

R-1The overlay exemption is reachable by an unprivileged attacker

F-7 requires the gate to tolerate overlay inodes, or it fail-closes every container; M-09 frames that as a scoping decision. But unprivileged user namespaces have permitted unprivileged overlayfs mounts since 5.11. A T-A adversary can unshare -Ur, mount an overlay, and execute from it, landing squarely in the ENODATA case the host gate has to exempt. The exemption containers need is the attacker's escape hatch.

Either deny overlay-backed exec outside an allow-listed runtime lineage, or make user.max_user_namespaces=0 a stated hard precondition for M-03. This deserves its own finding rather than a line in M-09.

F-7, M-09

R-2verify_file() fail-closes every container on the host

The function returns -EPERM on ENODATA. Loaded on any container host, that blocks every container exec — precisely the outcome F-7 warns about. BPF LSM programs are system-wide, not per-namespace, so the overlay exemption is a code requirement, not a deployment choice an operator makes later.

Appendix C, F-7

R-3exec_gate carries no runtime allow-list

DET-01 says to allow-list runc and containerd by verified parent digest. The illustrative gate does not: it denies all tmpfs inodes with i_nlink == 0 unconditionally. On runc ≤1.1.x, or on any rootless or fallback path on newer runc, that is every container start.

Appendix C, DET-01, F-5

R-4Denied verdicts are never cached, so the deny path is a DoS surface

Only approved verdicts enter bpf_inode_storage. An unprivileged loop of execve against unsigned binaries therefore forces an unbounded PKCS#7 verification per attempt, in kernel context. The §7 micro-benchmark measures the cold and warm allow paths; under enforcement the adversarial deny path is the one that decides whether the control is safe to enable.

F-10, §7, Appendix C

R-5The anon-exec predicate changes meaning with the /tmp backing

is_anon_exec_inode() denies by inode class on a tmpfs /tmp, but falls through to signature verification on an overlay or ext4 /tmp. G-4 records the coverage gap in one direction; the converse is not stated — the same pattern 1f produces two different policy outcomes depending on how a host mounts /tmp, which makes the control's behaviour un-auditable across a mixed fleet.

Appendix C, G-4, F-9

Verify before building

One cheap check that determines whether the load-bearing half of M-03 can exist at all.

R-6Is mmap_file in the sleepable LSM hook set?

Both bpf_get_file_xattr and bpf_verify_pkcs7_signature are KF_SLEEPABLE, so each leg of the gate must attach as lsm.s/. bprm_check_security is in the sleepable set. I am not confident mmap_file is, and the upstream selftests demonstrate signature verification on other hooks.

If it is not sleepable, the mmap_file(PROT_EXEC) leg will not load — and §1 stakes the entire deployment constraint (libc, ld.so, NSS modules, native extensions, vendor plugins) on that leg. Pin it against sleepable_lsm_hooks in kernel/bpf/bpf_lsm.c on the target kernel before any pilot work.

§1, Appendix C

Design and operational

R-7The i_version fallback puts the signing key on fleet hosts

Signing i_ino:i_generation:i_version produces a per-host value that cannot be generated at build time. That forces on-host signing, which collapses the offline-CA story the whole Appendix C pipeline rests on and hands a T-B adversary the key. Either drop the fallback or state plainly that it is detect-only.

§5.4

R-8No comparison against the incumbent controls

IPE, the Integrity Policy Enforcement LSM (merged around 6.12, worth confirming), already does fs-verity and dm-verity digest-based execution policy natively, with signed policy updates and a policy language. It is the closest existing thing to what is being hand-rolled here, and it is not mentioned. IMA appraisal and dm-verity are named but deferred to further work.

Since M-03's preconditions — immutable host, controlled supply chain, kernel ≥6.8, Secure Boot plus lockdown — largely describe hosts that could simply ship a verified image, the comparison against IPE, IMA-appraise and bootc/composefs is the decision an adopter actually faces. It belongs in the body, not the backlog.

§1, §6.2, §7

R-9fs-verity enablement and the package-update window are understated

Two costs are compressed into a single line of M-03. First, tune2fs -O verity is not settable on a mounted ext4, so existing fleets need offline filesystem work or reprovisioning — not a build-pipeline change. Second, there is no fs-verity or xattr hook in dpkg or rpm, so every package update leaves a window in which a replaced binary is executable and tagless. Under a fail-closed gate that is a self-inflicted outage, and the detect-only period will not surface it.

M-03, Appendix C signing pipeline

R-10Mode-2 memfd_noexec semantics on mixed 6.3–6.5 kernels

M-01 describes the later behaviour only — MFD_EXEC rejected with EACCES, MFD_NOEXEC_SEAL implied. My recollection is that mode 2 originally returned EACCES to flagless memfd_create callers and was changed during the 6.3–6.6 range because it broke userspace. If so, a fleet spanning those kernels will see two different behaviours from the same sysctl value. Worth pinning the commit before the M-01 rollout.
